# 技术调研报告

> 对应原始需求中的"产品或技术调研"。本文档论证：**智慧病房云边协同系统在演示阶段为何选 Docker Compose + 自研 FedAvg + YOLOv8n-pose INT8 的技术组合**，并给出面向真实病房部署的演进路径。

---

## 1. 调研背景

本项目"智慧病房云边协同系统"是典型的**边缘计算 + 医疗 IoT**场景，核心诉求：

1. **边缘自治**：病房断网时，边缘代理（Orange Pi 5）仍能独立完成姿态识别、跌倒检测、坠床预警、环境告警等本地决策，保证患者安全不中断。
2. **云边协同**：云端集中展示 1 个病区 3 张床位的实时状态、事件闭环、交接班摘要，并能下发模型灰度部署、环境控制指令。
3. **多源融合**：摄像头（YOLOv8n-pose 姿态）+ 床垫压力传感器（ESP32+FSR402）+ 输液监测 + 环境传感器四源融合，降低单一传感器误报。
4. **隐私合规**：原始视频留边缘端，仅上传事件摘要与脱敏证据，符合病房隐私要求。
5. **可演进**：从演示阶段的 Docker Compose 8 服务，演进到真实病房的 KubeEdge / K8s 多病区部署。

需要选择**边缘计算编排平台**、**边缘推理框架**、**视觉模型**、**通信协议**、**可靠性方案**、**联邦学习框架**六类技术。本文档逐一对比论证。

## 2. 边缘计算技术现状

### 2.1 什么是病房场景的边缘计算

边缘计算将算力从中心云下沉到病床旁的"边缘主机"，解决：
- **时延**：跌倒/坠床事件本地秒级识别，不依赖云端往返（云端往返典型 300-800ms，边缘本地 30-60ms）
- **带宽**：3 张床位 1080p 视频若全上云约 12 Mbps，边缘只传事件后 < 10 KB/s
- **可靠性**：病房网络偶发抖动或断网时，边缘仍可工作（自治），保证患者安全不中断
- **隐私**：患者面部/体态视频不出本地，仅上传事件摘要与脱敏截图

### 2.2 主流边缘计算框架

| 框架 | 厂商/社区 | 定位 | 是否适合病房 |
|------|-----------|------|--------------|
| **Docker Compose** | Docker 官方 | 单机/小集群容器编排 | 演示阶段首选 |
| **KubeEdge** | 华为开源/CNCF毕业 | K8s 原生云边协同 | 真实病房部署目标 |
| **OpenYurt** | 阿里开源/CNCF | K8s 无侵入边缘扩展 | 备选 |
| **K3s** | Rancher/CNCF | 轻量级 K8s 发行版 | 边缘单机可选 |
| **EdgeX Foundry** | Linux 基金会 | IoT 边缘中间件 | 设备接入层备选 |
| **Baetyl** | 百度开源 | 边缘计算框架 | 备选 |

## 3. 边缘计算平台对比

### 3.1 五大方案横向对比

| 维度 | Docker Compose | 原生 K8s | K3s | KubeEdge | EdgeX Foundry |
|------|---------------|---------|-----|----------|---------------|
| 定位 | 单机容器编排 | 容器编排平台 | 轻量 K8s | **云边协同平台** | IoT 边缘中间件 |
| 边缘自治（断网） | ⚠️ 需自建 | ❌ 无 | ⚠️ 弱 | **原生支持** | ⚠️ 部分 |
| 云边协同 | ❌ 无 | ❌ 无 | ⚠️ 需自建 | **核心能力** | ⚠️ 需自建 |
| 设备管理（IoT） | ❌ 无 | ❌ 无 | ❌ 无 | **Device CRD** | **强** |
| MQTT 集成 | 需自部署 | 需自部署 | 需自部署 | 内置 EventBus | 内置 |
| 边缘资源占用 | **低** | 高（>1GB） | 中（512MB） | 低（EdgeCore ~70MB） | 中 |
| 学习曲线 | **低** | 高 | 中 | 中高 | 中 |
| 演示阶段搭建成本 | **半天** | 2-3 天 | 1-2 天 | 3-5 天 | 2-3 天 |
| 适合演示阶段 | **是** | 否 | 否 | 否 | 否 |
| 适合真实病房交付 | 否（规模受限） | 过重 | 不解决自治 | **是** | 是（设备层） |

### 3.2 选型结论：演示阶段 Docker Compose，交付阶段 KubeEdge

**演示阶段（当前，3 床位 1 病区）选 Docker Compose**，理由：

1. **快速联调**：8 服务一键 `docker compose up`，半天即可完成端到端联调，不被平台学习成本拖慢。
2. **复用智能教室项目验证过的技术路线**：Vue / FastAPI / MQTT / MySQL / SQLite / Docker Compose 已在 edge 项目跑通，零学习成本。
3. **断网自治不依赖平台**：本项目断网自治由"边缘 SQLite 缓存 + `synced` 补传 + `event_id` 去重"三件套自实现，与平台解耦，Compose 完全够用。
4. **演示重点是业务闭环**：14 类事件 + 10 项智能功能 + 事件状态机，而非平台能力本身。

**交付阶段（真实病房，多病区 N 床位）演进到 KubeEdge**：

```
阶段一（当前，演示）：
  Docker Compose 本地 8 服务联调
  边缘自治 = SQLite + event_id 去重（自研）

阶段二（真实病房）：
  云端 K8s + KubeEdge CloudCore（多病区集中管理）
  病房 Orange Pi 5 加入集群运行 EdgeCore（边缘节点自治）
  设备接入走 Device CRD + Mapper
  断网自治升级为 MetaManager + 本地 SQLite 双保险
```

**降级路线（Plan B/C）**：
- **Plan B**：KubeEdge 单 master + 单边缘节点（至少演示 1 个真实边缘节点自治）+ 其余用 Compose 模拟
- **Plan C**：纯 Docker Compose 交付，本调研报告说明 KubeEdge 选型与未来演进路径

## 4. 边缘推理框架对比

目标硬件：Orange Pi 5（RK3588，6 TOPS NPU，8GB RAM）。

### 4.1 四大推理框架横向对比

| 维度 | ONNX Runtime | OpenVINO | TensorRT | **RKNN** |
|------|-------------|----------|----------|----------|
| 厂商 | 微软开源 | Intel 开源 | NVIDIA | **瑞芯微（RK3588 原厂）** |
| 目标硬件 | 通用 CPU/GPU | Intel CPU/iGPU/VPU | NVIDIA GPU | **RK3588 NPU** |
| RK3588 NPU 支持 | ❌ 不支持 | ⚠️ 间接（转 ONNX） | ❌ 不支持 | **原生支持** |
| YOLOv8-pose 支持 | ✅ | ✅ | ✅ | ✅（需转换） |
| INT8 量化 | ✅ | ✅ | ✅ | ✅ |
| 推理性能（YOLOv8n-pose） | 5-8 FPS（CPU） | 8-12 FPS | 不适用 | **15-30 FPS（NPU）** |
| 部署复杂度 | 低 | 中 | 低 | 中（需模型转换） |
| 模型转换工具 | 无需 | `.onnx -> .xml/.bin` | `.onnx -> .engine` | `.onnx -> .rknn` |
| 社区/文档 | 强 | 中 | 强 | 中（瑞芯微官方） |

### 4.2 选型结论：OpenVINO 为主 + RKNN 为目标硬件

**推荐组合：开发用 OpenVINO（x86 开发机快速验证），部署用 RKNN（Orange Pi 5 NPU 加速）**

1. **OpenVINO 作为开发期默认运行时**：
   - x86 开发机无需 NPU 即可跑通 YOLOv8n-pose
   - 与 ONNX 生态无缝衔接，模型转换成本低
   - 用于算法验证、精度回归、训练数据回流
2. **RKNN 作为目标硬件部署运行时**：
   - Orange Pi 5 自带 RK3588 NPU，原生支持 RKNN
   - INT8 量化后 6MB 模型，NPU 推理 15-30 FPS，满足实时姿态识别
   - 瑞芯微官方提供 `rknn-toolkit2` 模型转换工具链
3. **TensorRT 不适用于本项目**：目标硬件无 NVIDIA GPU，TensorRT 无法发挥优势
4. **ONNX Runtime 作为兜底**：若 RKNN 转换失败，可降级到 ONNX Runtime CPU 推理（性能下降但功能可用）

### 4.3 模型转换流水线

```
PyTorch (.pt)
  └─ export -> ONNX (.onnx)            # 通用中间格式
       ├─ OpenVINO (.xml/.bin)          # 开发机验证
       └─ rknn-toolkit2 (.rknn)         # Orange Pi 5 部署（INT8 量化）
```

## 5. 视觉模型对比

任务：病房床位姿态识别 + 跌倒/坠床/抽搐检测，要求轻量、实时、可在 NPU 量化。

### 5.1 四大视觉模型横向对比

| 维度 | YOLOv8n-pose | YOLOv10n | YOLO11n | MediaPipe Pose |
|------|-------------|----------|---------|----------------|
| 厂商 | Ultralytics | 清华/北航 | Ultralytics | Google |
| 任务 | **姿态 + 检测** | 检测 | 检测 | 姿态 |
| 跌倒检测 | **直接输出 posture + fall_score** | 需后处理 | 需后处理 | posture 但无 fall_score |
| 模型大小（FP16） | ~7 MB | ~5 MB | ~5 MB | ~10 MB |
| INT8 量化后大小 | **~6 MB** | ~4 MB | ~4 MB | 不支持 INT8 |
| 推理速度（RK3588 NPU） | **15-30 FPS** | 25-40 FPS | 25-40 FPS | 10-15 FPS（CPU） |
| 关键点输出 | 17 关键点 | 无 | 无 | 33 关键点 |
| 量化精度损失 | <2% mAP | <3% mAP | <3% mAP | 不适用 |
| 训练数据需求 | 中（COCO 预训练） | 中 | 中 | 不可训练 |
| RKNN 支持 | ✅ 成熟 | ✅ | ⚠️ 较新 | ❌ |
| 病房姿态识别契合度 | **最高** | 低 | 低 | 中 |

### 5.2 选型结论：YOLOv8n-pose INT8

**核心理由**：

1. **唯一原生支持"姿态 + 跌倒分"双输出**：本项目需要 `posture`（sitting/lying/standing/lying_edge/curled/seizing/falling）和 `fall_score` 两个维度，YOLOv8n-pose 一阶段输出，无需多模型串联。
2. **INT8 量化后 6MB，适合 Orange Pi 5 部署**：边缘主机内存仅 8GB，模型越小留给缓存与推理调度的空间越大。
3. **NPU 推理 15-30 FPS 满足实时性**：跌倒事件要求秒级识别，30 FPS 留足融合引擎与 MQTT 上报的时间预算。
4. **关键点可支撑异常体态识别**：17 个关键点可计算"蜷缩/前倾/抓胸"等异常体态，支撑 `abnormal_posture` 事件。
5. **RKNN 量化链路成熟**：瑞芯微官方与社区均有 YOLOv8-pose 转 RKNN 的完整教程，转换风险低。

**YOLOv10n / YOLO11n 不选的原因**：两者均为纯检测模型，无姿态输出，要实现跌倒检测需额外后处理（边界框 + 角度计算），增加边缘端算力负担与误报率。

**MediaPipe Pose 不选的原因**：
- 不支持 INT8 量化，无法在 NPU 加速
- 33 关键点冗余，病房只需要粗粒度姿态
- 训练不可定制，无法用病房困难样本微调

### 5.3 模型量化策略

```
训练阶段（云端）：
  YOLOv8n-pose.pt (FP32, ~22MB)
    └─ 病房困难样本微调（云边协同训练，见 §8）
    └─ 导出 ONNX
    └─ RKNN 量化校准（用病房脱敏截图做校准集）
    └─ INT8 .rknn (~6MB)

部署阶段（边缘）：
  model/deploy 主题灰度下发 -> Orange Pi 5 加载 .rknn
  推理引擎自动切换 model_version
```

## 6. MQTT vs HTTP 通信对比

### 6.1 横向对比

| 维度 | MQTT | HTTP | WebSocket |
|------|------|------|-----------|
| 通信模式 | **发布订阅** | 请求响应 | 双向长连接 |
| QoS 支持 | **0/1/2 三级** | 无 | 无 |
| 断线重连 | 自动（客户端库） | 需业务层实现 | 需业务层实现 |
| 单包开销 | **极小（2 字节头）** | 大（HTTP 头） | 中 |
| 多对多通信 | **天然支持（主题广播）** | 需多个端点 | 需多连接 |
| 适合 IoT 场景 | **是** | 否 | 部分 |
| 云端订阅多边缘 | **一个订阅通配 ward/+/node/+/** | 多次轮询 | 多连接 |
| 断网缓存配合 | **QoS1 + 本地队列天然契合** | 需自建重试 | 需自建重试 |

### 6.2 选型结论：MQTT（QoS 1）

**核心理由**：

1. **QoS 1 提供至少一次送达**：病房事件不可丢，QoS 1 配合 `message_id` 去重，等价于"恰好一次"语义，且开销远低于 QoS 2。
2. **发布订阅天然契合云边多对多**：3 个边缘节点向云端上报，云端向 3 个边缘节点下发指令，一个 broker 即可承载，无需 HTTP 轮询。
3. **断网缓存无缝衔接**：边缘 MQTT 客户端断线时消息进入本地队列，重连后自动补传，与 SQLite 缓存方案天然配合。
4. **单包开销极小**：病房每秒数百条观测数据，MQTT 2 字节头远优于 HTTP 的数百字节头。
5. **生态成熟**：Mosquitto 开源稳定，paho-mqtt / mqtt.js 客户端库齐全，edge 项目已验证。

### 6.3 HTTP 的辅助角色

MQTT 不替代 HTTP，两者分工：
- **MQTT**：边缘 -> 云端的实时事件/观测/心跳上报，云端 -> 边缘的指令下发
- **HTTP**：护士站前端 -> 云端后端的 RESTful 查询与操作（事件确认、交接班生成、模型下发触发）
- **WebSocket**：云端后端 -> 前端的实时事件推送（告警闪烁、床位状态更新）

## 7. 通信可靠性方案对比

病房事件（尤其 P1 跌倒/坠床）不可丢失、不可重复，需在 MQTT QoS 1 基础上叠加业务层可靠性。

### 7.1 候选方案对比

| 方案 | 可靠性 | 实现复杂度 | 断网自治 | 重复事件 |
|------|--------|-----------|---------|---------|
| 纯 MQTT QoS 0 | 低 | 低 | ❌ 丢消息 | - |
| 纯 MQTT QoS 1 | 中 | 低 | ⚠️ 断网时队列丢 | 有重复 |
| MQTT QoS 1 + HTTP 重试 | 中 | 中 | ⚠️ 依赖 HTTP 可达 | 有重复 |
| **MQTT QoS 1 + SQLite 缓存 + event_id 去重** | **高** | 中 | **✅** | **无** |
| MQTT QoS 2 | 高 | 高 | ❌ 性能差 | 无 |

### 7.2 选型结论：MQTT QoS 1 + SQLite 缓存 + event_id 幂等去重

**三件套方案**（已在 edge-agent 落地）：

1. **QoS 1**：保证至少一次送达，断网时消息不丢。
2. **边缘 SQLite 缓存**：每条事件落盘后再发，发送成功标记 `synced=1`，断网期间持续写入本地表。
3. **`event_id` 全局唯一去重**：云端按 `event_id` 去重，断网补传产生的重复消息被自动丢弃。

```text
边缘端事件流：
  融合引擎产出事件
    -> 写入 SQLite (synced=0)
    -> MQTT 发布 QoS 1
    -> 收到云端 PUBACK
    -> 更新 SQLite synced=1

断网场景：
  写入 SQLite 持续累积 (synced=0)
  恢复后按时间序补传
  云端按 event_id 去重，丢弃重复
```

**优势**：业务层自实现，与平台解耦（Docker Compose / KubeEdge 均可），不依赖 QoS 2 的高开销握手。

## 8. 联邦学习框架对比

本项目创新点之一：云边协同训练，让 3 个床位边缘模型在不共享原始视频的前提下，聚合梯度更新全局模型，持续降低误报率。

### 8.1 候选方案对比

| 维度 | Flower | NVIDIA FLARE | **自研（基于 FedAvg）** |
|------|--------|--------------|----------------------|
| 厂商/社区 | 调研社区开源 | NVIDIA | **本项目自研** |
| 学习曲线 | 中 | 高 | **低（团队已掌握）** |
| 病房场景定制 | 通用框架，需适配 | 通用框架，需适配 | **按病房场景定制** |
| 梯度聚合算法 | 内置 FedAvg + 扩展 | 内置多种 | **自研同步 FedAvg + 半异步陈旧度加权** |
| 异步调度支持 | ⚠️ 需扩展 | ✅ | **✅ 自研半异步** |
| 与 MQTT 链路集成 | 需额外适配 | 需额外适配 | **原生复用 MQTT 训练主题** |
| 困难样本回流 | 需自建 | 需自建 | **与云端扩散模型联动** |
| 代码量 | 大（框架本身） | 大 | **小（~500 行核心）** |
| 体现项目创新点 | ❌ 用现成框架 | ❌ 用现成框架 | **✅ 体现技术原创性** |

### 8.2 选型结论：自研 FedAvg + 半异步陈旧度加权

**核心理由**：

1. **体现项目创新点**：赛事评分重视技术原创性，自研训练调度框架（同步 FedAvg + 半异步陈旧度加权）是核心创新点之一，用现成 Flower 框架无法体现。
2. **按病房场景定制**：病房数据量小、节点数少（3 床）、网络偶发抖动，通用框架的复杂调度反而过重；自研可精准匹配"3 节点 + 困难样本回流 + 灰度部署"链路。
3. **与 MQTT 业务链路解耦**：训练主题 `training/{job_id}/node/{node_id}/{command,update}` 与实时业务主题隔离，自研调度器直接订阅，无需引入额外 RPC 框架。
4. **与云端扩散模型联动**：自研框架可与云端扩散模型（困难样本生成）无缝衔接，形成"误报回流 -> 扩散生成 -> 联邦训练 -> 灰度下发"闭环。
5. **三阶段渐进**：
   - 阶段 A：同步 FedAvg（所有节点齐齐上报再聚合，基线）
   - 阶段 B：半异步陈旧度加权（超时窗口 + 最小参与节点数 + 陈旧度权重）
   - 阶段 C：异常剔除 + 训练日志全链路（参与节点/样本数/梯度摘要/耗时/精度/带宽/异常原因）

### 8.3 降级路线

- 若半异步（阶段 B）开发受阻，降级为同步 FedAvg（阶段 A）+ 固定权重平均，保留核心创新点。
- 若梯度聚合精度不达标，降级为"只聚合模型版本，不聚合梯度"（参数服务器模式简化版）。

### 9.2 病房/养老同类方案对比

| 方案类型 | 典型做法 | 不足 | 本项目改进 |
|----------|----------|------|-----------|
| 纯云端方案 | 摄像头视频全传云端，云端识别 | 断网即瘫痪、时延高、隐私风险 | 边缘自治 + 仅传事件摘要 |
| 纯本地方案 | 呼叫按钮 + 床垫报警 | 无集中监控、无趋势分析、难扩展 | 云端护士站 + 交接班摘要 |
| 单传感器方案 | 仅床垫或仅摄像头 | 误报率高（床垫误判翻身、摄像头遮挡） | 四源融合 + 规则引擎 |
| 商业封闭方案 | 整体采购黑盒系统 | 不可定制、成本高 | 开源自研 + 可演进 |
| **云边协同（本项目）** | 边缘多源融合 + 云端集中 + 协同训练 | - | **兼顾自治、集中、隐私、演进** |

## 10. 选型结论汇总表

| 技术类别 | 选定方案 | 备选方案 | 选定理由 |
|---------|---------|---------|---------|
| 边缘编排平台（演示） | **Docker Compose** | K3s | 8 服务一键联调，复用 edge 项目路线 |
| 边缘编排平台（交付） | **KubeEdge**（演进目标） | OpenYurt | 原生边缘自治 + 设备 CRD + CNCF 毕业 |
| 边缘推理框架（开发） | **OpenVINO** | ONNX Runtime | x86 开发机快速验证，ONNX 生态无缝 |
| 边缘推理框架（部署） | **RKNN** | TensorRT（不适用） | RK3588 NPU 原生支持，INT8 15-30 FPS |
| 视觉模型 | **YOLOv8n-pose INT8** | YOLOv10n / YOLO11n / MediaPipe | 唯一原生姿态 + 跌倒分双输出，6MB 量化 |
| 通信协议 | **MQTT QoS 1** | HTTP / WebSocket（辅助） | 发布订阅 + QoS + 低开销 + 断网缓存契合 |
| 可靠性方案 | **QoS 1 + SQLite 缓存 + event_id 去重** | QoS 2 | 业务层自实现，平台解耦，开销低 |
| 联邦学习框架 | **自研 FedAvg + 半异步陈旧度加权** | Flower / NVIDIA FLARE | 体现创新点，病房场景定制，与 MQTT 联动 |
| 数据库（云端） | **MySQL 8.0** | PostgreSQL | edge 项目已验证，11 表 ORM 成熟 |
| 数据库（边缘） | **SQLite** | - | 嵌入式零运维，断网缓存天然契合 |
| 前端框架 | **Vue 3 + ECharts** | React | edge 项目已验证，护士站组件化复用 |
| 后端框架 | **FastAPI** | Flask / Django | 异步 + Swagger + 类型标注，edge 项目已验证 |
