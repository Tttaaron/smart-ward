### 3.1.2 数据流向

系统有两条核心数据流：

**上行（边缘 -> 云端）**：传感器采集 -> 边缘融合推理 -> MQTT 上报 -> 云端入库 -> WebSocket 推送护士站

```
传感器 → 采集适配器 → 推理引擎 → 融合引擎 → SQLite缓存 → MQTT发布
                                                      ↓
                                              云端MQTT处理器
                                                      ↓
                                        MySQL入库 + WebSocket广播
                                                      ↓
                                              护士站大屏展示
```

**下行（云端 -> 边缘）**：护士站操作 -> 云端 API -> MQTT 下发 -> 边缘执行

```
护士点击"到场" → POST /api/events/{id}/ack → MQTT发布ack
                                              ↓
                                        边缘收到ack回调
                                        （记录处置状态）
```

### 3.1.3 控制流向

| 控制指令 | 来源 | MQTT 主题 | 边缘处理 |
|---|---|---|---|
| 告警确认 | 护士站 | `ward/{ward_id}/alert/{event_id}/ack` | 记录处置状态 |
| 环境控制 | 护士站/自动 | `node/{node_id}/config/set` | 转发设备网关（演示仅日志） |
| 模型部署 | 管理员 | `node/{node_id}/model/deploy` | `inference.load_model()` 切换版本 |
| 模型回滚 | 管理员 | `node/{node_id}/model/rollback` | `inference.rollback()` 回退版本 |

## 3.3 部署架构

### 3.3.1 演示阶段：Docker Compose 单机

演示阶段（3 床位 1 病区）采用 Docker Compose 单机编排，8 服务一键启动：

```yaml
# docker-compose.yml 核心结构
services:
  mqtt-broker:     # Mosquitto 1884
  mysql:            # MySQL 8.0 3308
  cloud-backend:    # FastAPI 8001
  training-coordinator:  # FastAPI 8002
  cloud-frontend:   # Vue nginx 8081
  edge-bed-01:      # 边缘代理 B01（fall,nurse_call,fall_prediction,seizure）
  edge-bed-02:      # 边缘代理 B02（bed_leave,night_wandering,long_still,bedsore_risk）
  edge-bed-03:      # 边缘代理 B03（environment_anomaly,door_departure,abnormal_posture,device_fault）
```

**选 Docker Compose 的理由**：
1. 8 服务一键 `docker compose up`，半天完成端到端联调
2. 复用智能教室项目验证过的技术路线，零学习成本
3. 断网自治由"SQLite 缓存 + synced 补传 + event_id 去重"自实现，与平台解耦

### 3.3.2 交付阶段：KubeEdge 云边集群

真实病房（多病区 N 床位）演进到 KubeEdge：

```
阶段一（当前，演示）：
  Docker Compose 本地 8 服务联调
  边缘自治 = SQLite + event_id 去重（自研）

阶段二（真实病房）：
  云端 K8s + KubeEdge CloudCore（多病区集中管理）
  病房 Orange Pi 5 加入集群运行 EdgeCore（边缘节点自治）
  设备接入走 Device CRD + Mapper
  断网自治升级为 MetaManager + 本地 SQLite 双保险
```

**图 3-3 部署演进路线**

KubeEdge 的核心优势：
- **原生边缘自治**：断网时 EdgeCore 本地继续运行，恢复后自动同步
- **Device CRD**：统一设备接入抽象（摄像头/床垫/环境）
- **云边协同**：云端集中管理多病区边缘节点

### 3.3.3 降级路线

| 方案 | 说明 | 适用场景 |
|---|---|---|
| Plan A | KubeEdge 完整部署 | 真实病房交付 |
| Plan B | KubeEdge 单 master + 单边缘节点 + 其余 Compose 模拟 | 至少演示 1 个真实边缘节点自治 |
| Plan C | 纯 Docker Compose 交付 + 调研报告说明 KubeEdge 演进路径 | 时间不足时 |

## 3.4 技术选型

### 3.4.1 选型结论汇总表

| 技术类别 | 选定方案 | 备选 | 选定理由 |
|---|---|---|---|
| 边缘编排（演示） | **Docker Compose** | K3s | 8 服务一键联调，复用 edge 项目路线 |
| 边缘编排（交付） | **KubeEdge** | OpenYurt | 原生边缘自治 + Device CRD + CNCF 毕业 |
| 推理框架（开发） | **OpenVINO** | ONNX Runtime | x86 开发机快速验证，ONNX 生态无缝 |
| 推理框架（部署） | **RKNN** | TensorRT | RK3588 NPU 原生支持，INT8 15-30 FPS |
| 视觉模型 | **YOLOv8n-pose INT8** | YOLOv10n / YOLO11n / MediaPipe | 唯一原生姿态+跌倒分双输出，6MB 量化 |
| 通信协议 | **MQTT QoS 1** | HTTP / WebSocket（辅助） | 发布订阅 + QoS + 低开销 + 断网缓存契合 |
| 可靠性方案 | **QoS 1 + SQLite + event_id 去重** | QoS 2 | 业务层自实现，平台解耦，开销低 |
| 联邦学习 | **自研 FedAvg + 半异步陈旧度加权** | Flower / NVIDIA FLARE | 体现创新点，病房场景定制，与 MQTT 联动 |
| 数据库（云端） | **MySQL 8.0** | PostgreSQL | edge 项目已验证，11 表 ORM 成熟 |
| 数据库（边缘） | **SQLite** | - | 嵌入式零运维，断网缓存天然契合 |
| 前端框架 | **Vue 3 + ECharts** | React | edge 项目已验证，护士站组件化复用 |
| 后端框架 | **FastAPI** | Flask / Django | 异步 + Swagger + 类型标注 |

### 3.4.2 选型原则

1. **复用优先**：能复用智能教室项目验证过的技术就不引入新栈，降低团队学习成本
2. **平台解耦**：断网自治、事件可靠性由业务层自实现，不绑定特定编排平台
3. **创新可证**：联邦学习自研而非用现成框架，体现赛事要求的技术原创性
4. **演进可达**：演示用 Compose，交付有清晰到 KubeEdge 的演进路径，不做技术死胡同

> 各技术类别的详细对比论证见 `docs/09-技术调研报告.md` §3-§8，边缘模型详细对比见 `docs/02-边缘模型选型对比.md`。
